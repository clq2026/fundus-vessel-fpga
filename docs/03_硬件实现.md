# 03 硬件实现

## 3.1 冻结规格

规格文件：`hls/vessel_prj/vessel_top.hpp`（常量在此冻结）

| 参数 | 值 |
|---|---|
| 图像尺寸 H × W | 605 × 700（一帧 423,500 像素） |
| 中值窗口 `MED_K` | 3（3×3，半径 1） |
| 黑帽窗口 `BH_K` | 11（11×11 **矩形**，半径 5） |
| 数据位宽 | 8 bit 无符号 |
| 目标时钟 | 10 ns（100 MHz） |
| 目标器件 | `xc7z020clg400-1` |

## 3.2 边界语义

硬件要与 Python/OpenCV 参考逐像素一致，边界处理是最容易出错的地方。三级的越界规则各不相同：

| 算子 | 越界处理 |
|---|---|
| 中值 3×3 | `BORDER_REPLICATE`，越界坐标钳位到最近的有效行/列 |
| 膨胀 11×11 | 越界填 **0**（对取最大无影响） |
| 腐蚀 11×11 | 越界填 **255**（对取最小无影响） |
| 黑帽 | `erosion(dilation(med)) − med`，**饱和减法**，结果截断到 [0, 255] |

## 3.3 流式结构

像素逐个流入，不使用整帧缓存。顶层用 `#pragma HLS DATAFLOW` 建立任务级流水线：

```
AXI 输入
  → [复制补边 R=1] → 中值窗口 3×3 ──┬─────────────────────────────┐
                                     │                             │
                                     ├→ 延迟 FIFO（深度 16384）    │
                                     │                             ↓
                                     │                    [填 0 补边 R=5] → 膨胀窗口 11×11
                                     │                                            ↓
                                     └─────────────────────→ [填 255 补边 R=5] → 腐蚀窗口 11×11
                                                                                   ↓
                                                        黑帽 = 腐蚀结果 − 中值（对齐后相减）
                                                                                   ↓
                                                                              AXI 输出
```

三个组成单元：

**补边单元（pad）**：把 H×W 的像素流扩展成 (H+2R)×(W+2R) 的规则流，
三种边界语义（复制 / 常量 0 / 常量 255）在补边阶段一次解决，
后续窗口算子内部不含任何边界分支。

其中「复制补边」采用双缓冲 ping-pong：输出第 r 行的同时，在同一个列循环里把下一行所需的源行
预读进另一块行缓存。这一点是性能关键——若改回"读满一行再输出一行"的写法，
两段因数据依赖而串行，平均变成 2 拍/像素；由于它位于流水线第一级，会把整条链拖慢一倍
（实测单帧 866,656 拍 ≈ 8.67 ms，修复后降到 442,744 拍 ≈ 4.43 ms）。

**窗口核心（window_core）**：2R 条行缓存（拆成独立 RAM_2P）+ K×K 寄存器窗口，
每拍左移一列、最右列从行缓存补入。

**延迟 FIFO**：中值结果要等膨胀与腐蚀两级窗口填充完成（约 2 × 3555 拍）后才能与之相减，
用深度 16384 的内部 FIFO 暂存对齐，约占 8 块 BRAM。深度不足会死锁，不能随意调小。

**中值排序网络**：3×3 的 9 个数走 36 个比较器的奇偶排序网络，取排序后第 5 个（index 4）。

## 3.4 接口

| 接口 | 协议 | 说明 |
|---|---|---|
| 输入像素 | AXI4-Stream，8 bit | 每帧最后一个像素带 `TLAST` |
| 输出像素 | AXI4-Stream，8 bit | 每帧最后一个像素带 `TLAST` |
| 控制 | AXI4-Lite（`ap_start` / `ap_done` / `ap_idle`） | 基地址 `0x40000000` |

硬件只输出黑帽**原始差值**（约 0–100），不做归一化；
MINMAX 归一化、Otsu、后处理都在 PS 端完成，这样硬件不需要整帧统计。

## 3.5 为什么不用整帧缓存版

另一种直观做法是把整帧存进 BRAM 再做窗口运算。实测不可行：
每个像素要从同一块大 BRAM 同时读 121 个数，BRAM 读端口不够，
HLS 调度器搜索空间爆炸——综合跑了 1 小时以上没有结果（CPU 持续满载），
且中值级已经报出 `Final II = 9`。改成行缓存版后 II = 1，综合只需几分钟。

## 3.6 验证

| 阶段 | 结果 |
|---|---|
| C 仿真（两张图 × 423,500 像素） | 与 Python 参考**不一致像素 0**（`max_diff = 0`） |
| C/RTL 协同仿真 | PASS，RTL 输出与 C 仿真一致 |
| 协同仿真节拍 | 442,744 拍 ≈ 4.427 ms/帧（≈ 226 fps） |
| 板上实测 | 4.476 ms/帧，与协同仿真相差 1.1% |

协同仿真与板上实测只差 1.1%，说明系统集成没有引入额外瓶颈，也说明仿真模型可信。

运行方式（Vitis HLS 2022.2，Linux）：

```bash
cd hls/vessel_prj
vitis_hls -f run_hls.tcl          # 建工程 + C 仿真
vitis_hls -f run_hls.tcl cosim    # 追加 C/RTL 协同仿真
vitis_hls -f run_hls.tcl synth    # 追加综合并导出 IP
```

测试向量由 `python工具/gen_test_vectors.py` 生成，路径由 tcl 脚本按所在目录推导为绝对路径。
