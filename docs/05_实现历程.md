## 5.2 各阶段要点

**阶段 1–2：算法原型与定版**

先实现 V1 基础流程（绿通道 → 中值 → 黑帽 → 固定阈值），再迭代到 V2
（加 CLAHE、Otsu、FOV、删小块），并试过 V3（四方向线检测）。
V3 在 STARE 上 Dice 只提升 0.0077、DRIVE 上下降 0.0013，复杂度却显著增加，因此不采用。
最终以 V2 冻结硬件规格：605 × 700、中值 3×3、黑帽 11×11 矩形核、8 bit、100 MHz。

**阶段 3：HLS IP 设计**

最初采用整帧缓存结构，实测不可行：每个像素要从同一块 BRAM 同时读 121 个数，
读端口不够，综合跑了 1 小时以上没有结果，中值级已报 `Final II = 9`。
改为行缓存流式结构后 II = 1，综合只需几分钟。

**阶段 4：IP 验证与一次性能修复**

C 仿真在两张图共 847,000 个像素上与 Python 参考完全一致。
协同仿真初期单帧 866,656 拍（≈ 8.67 ms），定位到原因是「复制补边」写成了
"读满一行再输出一行"，两段因数据依赖串行，平均 2 拍/像素；
由于它位于流水线第一级，整条链被拖慢一倍。
改成双缓冲 ping-pong 后降到 442,744 拍（≈ 4.43 ms），与板上实测相差 1.1%。

**阶段 5：系统集成**

Block Design 用 tcl 脚本构建，并在 `verify_bd.tcl` 里加了几条硬检查，
把曾经踩过的坑变成自动检查项：

- V-06b：复位辅助脚电平检查。之前因为辅助脚电平不确定导致上板后 PL 一直处于复位态。
- V-08b：DMA 单次传输长度上限检查。默认 14 位（16383 字节）会把一帧 423,500 字节
  静默截断成 13900 字节，MM2S 提前发出 TLAST 使 IP 挂死；脚本内已强制 26 位并加检查。

**阶段 6：上板联调**

确立三条 DMA 使用约定：启动顺序（两通道复位 → `ap_start` → 写地址 → 写长度）、
完成判据（状态寄存器 bit1 `Idle`，而非中断位）、以及"被中止的传输会污染 IP 内部状态，
只有重载 bitstream 能清除"。
后者是最隐蔽的一个坑：被污染后运行耗时完全正常，但约 85% 的像素是错的，
因此正确性判据必须是逐像素比对，而不是"没有抛异常"。

**阶段 7：性能评测**

先测核心算子，再测端到端，最后做压力测试。
核心算子区分吞吐口径（4.476 ms，223 fps）与延迟口径（9.4 ms，105 fps），
两者相差的约 5 ms 全部来自 ARM 侧内存操作。
另外发现 FOV 生成是当时最大的瓶颈（占纯软件总时长 81%），
把幂等的闭运算从 50 次减到 1 次后降到 28%，端到端加速比从 1.12× 提到 1.66×。

**阶段 8：真实拍摄链路**

标准数据集之外要处理真实拍摄的照片，此时 Otsu 自动 FOV 会失效（白底场景下把整幅图判为有效区域）。
改用 R−B 色度分割定位眼底圆生成圆形 FOV，Dice 从 0.0000 恢复到 0.5907。
拍摄方式上，对比过 USB 摄像头与手机拍照：绿通道对比度分别是 0.3 和 5.2，
差距过大，因此选择手机拍照路线。

## 5.3 几个有数据支撑的取舍

| 决策 | 依据 |
|---|---|
| 只把中值 + 黑帽放进硬件 | 占绝大部分计算量，纯局部窗口运算，8 bit 直连无需位宽转换 |
| 弃用整帧缓存，改行缓存 | 整帧版综合 1 小时无结果且 II = 9；行缓存版 II = 1 |
| 不采用 V3 四方向线检测 | STARE Dice +0.0077、DRIVE −0.0013，收益不抵复杂度 |
| FOV 闭运算只做 1 次 | 闭运算幂等，1 次与 50 次在 20 张图上差异 0 像素 |
| 实拍用圆形 FOV | Otsu 自动 FOV 得 0.0000，圆形 FOV 得 0.5907 |
| 拍摄用手机拍照而非 USB 摄像头 | 绿通道对比度 5.2 对 0.3 |
| 定位用色度分割而非 Hough | Hough 在白球背景上检出 21 个候选圆，选圆打分失效（选中 r=124，真值 280） |
