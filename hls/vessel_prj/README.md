# HLS 血管加速 IP 工程（规格 v1.0）

把软件流水线中的 **中值滤波 3×3** 和 **黑帽 11×11 矩形核** 用 Vitis HLS 实现，
供 PYNQ-Z2（Zynq XC7Z020）调用。算法行为与 Python/OpenCV 参考**逐像素一致**。

## 一、文件说明

| 文件 | 作用 |
|---|---|
| `vessel_top.hpp` | 冻结常量（H=605, W=700, 3×3, 11×11）、AXI-Stream 类型、顶层声明 |
| `vessel_top.cpp` | 行缓存 streaming 实现：补边 → 中值 → 膨胀 → 腐蚀 → 黑帽，DATAFLOW 流水线 |
| `tb_vessel.cpp` | 测试台：读测试向量、调用 IP、与参考逐像素对比 |
| `run_hls.tcl` | 一键建工程/仿真/综合脚本 |
| `native_sim/` | 仅本机无 HLS 时用 g++ 验证的头文件替身，**不导入 HLS 工程** |
| `../test_vectors/` | 测试向量（输入 + 参考输出，由 Python 生成） |

## 二、算法与边界语义（必须与参考一致）

```
输入(CLAHE后灰度) → 中值3x3[边界复制] → 膨胀11x11[越界=0]
                 → 腐蚀11x11[越界=255] → 输出 = 腐蚀结果 − 中值图(饱和减)
```

- 中值：3×3 九个数走 36 比较器的奇偶排序网络，取排序后第 5 个（index 4）。
- 膨胀 = 11×11 取最大；腐蚀 = 11×11 取最小；黑帽 = 闭运算 − 中值图，差值截断在 [0,255]。
- 硬件只输出黑帽**原始差值**（约 0~100），MINMAX 归一化/Otsu/后处理都在 ARM 软件端。

## 三、硬件实现结构：行缓存 streaming（II=1）

像素逐个流入，不使用整帧缓存，任务级流水线（`#pragma HLS DATAFLOW`）：

```
AXI读入 → [复制补边] → 中值窗口3x3 → med ──┬→ [填0补边] → 膨胀窗口11x11
                                           │                     │
                                           └ 延迟FIFO(16384)     ↓
                                            med_delay [填255补边] → 腐蚀窗口11x11
                                                                 │
                         黑帽 = 腐蚀 − 中值(对齐) ←───────────────┘
→ AXI输出
```

- **补边单元（pad）**：把 H×W 流扩展成 (H+2R)×(W+2R) 规则流，边界语义在补边阶段
  一次解决（复制 / 常量 0 / 常量 255）；后续窗口算子不含任何边界分支。
  - 「复制补边」`pad_replicate` 采用**双缓冲 ping-pong**：输出第 pr 行的同时在同一个
    `col_loop` 里把下一行所需的源行预读进另一块 `rowbuf`（两块互不冲突，可 II=1）。
    **不要改回「读满一行 → 再输出一行」的写法**——那样两段因数据依赖串行，
    会变成平均 2 拍/像素，而它是流水线第一级，会把整条链拖慢一倍
    （2026-09-28 实测单帧 866656 拍 ≈ 8.67ms；修复后预计 ~426800 拍 ≈ 4.27ms）。
- **窗口核心（window_core）**：2R 条行缓存（拆成独立 RAM_2P）+ K×K 寄存器窗，
  每拍左移一列、右列从行缓存补入。
- **延迟 FIFO**：中值像素要等膨胀+腐蚀两级窗口填充（约 2×3555 拍）后才能相减，
  用深度 16384 的内部 FIFO 暂存对齐（约占 8 块 BRAM）。深度不够会死锁，不能随意调小。

### 为什么不用整帧缓存版

整帧缓存版每个像素要从同一块大 BRAM 同时读 121 个数，BRAM 读口不够，
HLS 调度器搜索空间爆炸——实测综合 1 小时以上无结果（CPU 持续满载），
且中值级已报 `Final II = 9`。行缓存版 II=1、综合只需几分钟。

## 四、没有 Vitis 时：用普通 g++ 做本地 C++ 仿真（已验证通过）

用 `native_sim/stubs` 里的 `hls_stream.h`、`ap_axi_sdata.h` 替身代替 Vitis 官方头，
普通 g++ 即可编译运行真实 C++ 代码。实测两张测试图各 423500 像素，
与 Python 参考**全部一致（max_diff=0）**。

- **Windows 一键**：双击 `run_native.bat`（自动编译 + 运行 + 逐像素对比），需要 PATH 里有 g++。
- **Linux / macOS**：

  ```bash
  g++ -O2 -std=c++14 -I native_sim/stubs -I . tb_vessel.cpp vessel_top.cpp -o vessel_sim
  ./vessel_sim
  ```

- 局限：本地仿真**只验证算法逻辑**，替身不模拟 FIFO 深度/反压，
  不能综合、不反映真实电路资源/时序——那必须在 Vitis HLS 里做。
- 这些替身头文件**不加入** Vitis 工程。

## 五、在 Vitis HLS 2022.2 中操作

### 方式 A：图形界面
1. 新建 Vitis HLS Project，器件选 `xc7z020clg400-1`（PYNQ-Z2）。
2. Design Files 添加 `vessel_top.cpp`；Test Bench 添加 `tb_vessel.cpp`。
3. Top Function 设为 `vessel_top`。
4. 运行 **C Simulation**；控制台应输出两张图各自
   `[通过] 423500 个像素全部一致 (max_diff=0)`。

### 方式 B：命令行（在本目录）
```bash
vitis_hls -f run_hls.tcl          # 建工程 + C 仿真
vitis_hls -f run_hls.tcl cosim    # 加做 C/RTL 协同仿真
vitis_hls -f run_hls.tcl synth    # 加做综合并导出 IP
```

> 测试向量路径由脚本自动设为绝对路径（基于 tcl 所在目录推导），
> C 仿真工作目录变化也不会找不到文件。

## 六、验收标准

- C 仿真：im0082、im0002 两图，共 2×423500 像素，**不一致像素数必须为 0**。
- 综合后查看：
  - 各任务 II 是否为 1；
  - 资源（LUT/FF/BRAM/DSP）占 Z7020 比例是否有余量；
  - 目标周期 10ns（100MHz）时序能否收敛；
  - 帧延迟（应约为 PIX_TOTAL + 流水线填充）。
- 协同仿真：RTL 级输出与 C 仿真一致。
